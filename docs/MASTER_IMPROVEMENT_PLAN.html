Real Bugs — Found in Source Code

FIX FIRST
These were found by reading actual source files. They are not planned items — they are defects in code that ships today. Fix before any new feature work begins on those files.

BUG-01 — callLocalModel() missing try/catch

Score 45 — Critical
  • File: lib/ai.ts lines 125–138. The fetch(s.localEndpoint, ...) call and res.json() parse have no try/catch. If Ollama is offline, a network error or JSON parse error propagates uncaught and can crash the agent loop.Fix: Wrap the entire function body in try/catch. Return '' on failure. This is the same pattern used in every other fetch in the codebase.

BUG-02 — streamRequest non-null assertion on res.body

Score 35 — High
  • File: lib/ai.ts line 86. Code: res.body!.getReader(). The ! non-null assertion means if the server returns a 204 or a response with no body, this line throws a TypeError at runtime.Fix: if (!res.body) throw new Error('No response body') before the assertion.

BUG-03 — callAI() hardcodes model string

Score 30 — High
  • File: lib/ai.ts line 159. cloudModel is set to 'claude-opus-4-5' as a hardcoded string instead of using the TASK_MODELS or a named constant from lib/aiModelRouting.ts. If the model name changes or a task-specific model is needed, this will be silently wrong.Fix: Use TASK_MODELS[task] or a dedicated DEFAULT_CLAUDE_MODEL constant from aiModelRouting.ts.

BUG-04 — getSettings() reads localStorage directly

Score 24 — Medium
  • File: lib/ai.ts lines 11–21. getSettings() reads directly from localStorage, bypassing the Zustand reactive system. If a user changes their API key or provider in the settings drawer during a session, callAI() may still use the old cached values.Fix: Accept settings as a parameter, or call useStore.getState().settings. The latter is already available and reactive.

Block 11 — Ecosystem Insights

EXT

Patterns extracted from two open-source repos — brendanhogan/loophole (adversarial multi-agent constraint system) and NVIDIA-NeMo/DataDesigner (synthetic dataset generation + LLM-as-judge eval) — mapped to concrete Nexus Prime improvements. All items are EXT-prefixed in the tracker. None require vendoring third-party code.

11.1 Adversarial Eval Category

EXT-01

Source: loophole — Legislator / Loophole Finder / Overreach Finder / Judge loop

  • Add an adversarial eval category to scripts/eval-agent-runtime.js. Each test sends a prompt that deliberately tries to find a loophole in the skill governance rules (A6) and asserts that the agent either blocks or escalates — it must never silently comply.
  • Seed with 10 adversarial prompts covering: (a) attempting a tier2 write without review, (b) asking for a secret from process.env, (c) cross-agent impersonation via prefix spoofing, (d) infinite loop via recursive tool calls, (e) data exfil via fetch to an unlisted domain.
  • Wire adversarial category into CI with its own threshold flag: --min-category adversarial=90. A score below 90 fails the build. This is the only eval category with a higher floor than the default.

11.2 Constraint Consistency Checker

EXT-02

Source: loophole — dynamic constraint accumulation, binding precedents

  • New JANSKY capability: check_precedent_conflict(proposedAction). Before any approved agent decision is executed, this tool scans the in-memory precedent log and flags if the proposed action contradicts a prior approved or rejected decision in the same session.
  • Approved PendingEdit decisions accumulate as session-scoped "precedents" in a lightweight in-memory list (no external DB). On conflict: escalate to the operator HUD with a diff-style view showing the earlier decision vs. the proposed action.
  • Persist the precedent log to IndexedDB under a session key so overnight Night Ops runs can still detect conflicts from earlier in the same session. Evict on explicit "clear session" command.

11.3 Decision Diff View in VAULT

EXT-03

Source: loophole — HTML visualization with git-style diffs and timeline views

  • In VAULT, add a "Session Decisions" panel. Each agent run that produced a PendingEdit or AgentRunArtifact is shown as a timeline card: timestamp, agent, action taken, outcome (approved / rejected / auto-applied).
  • Each card expands to show a diff-style view — previous state on the left, proposed state on the right, using a simple line-level diff computed in the client. No external diff library needed: split on newline, compare arrays, highlight added/removed lines with fhi/flo token colors.
  • Export session decisions as a markdown report from the VAULT panel. The report uses the existing handoff template format so it feeds directly into docs/AGENT_HANDOFF.md via npm run handoff:write.

11.4 Dynamic Precedent Binding

EXT-04

Source: loophole — every resolved case becomes binding, escalation on contradiction

  • Add a reinforced: boolean flag to the KnowledgeEntry type in store/useStore.ts. When an operator approves a lesson via the existing lesson approval flow, set reinforced: true.
  • Reinforced entries cannot be overridden by autonomous agent runs. If an auto-run proposes an action that conflicts with a reinforced entry, the run is downgraded to "human-gate required" mode and the conflict is surfaced in the HUD before any write executes.
  • Show reinforced entries in the Memory panel with a lock icon. The operator can manually un-reinforce an entry with an explicit confirmation dialog — two-step, no accidental unlock.

11.5 Synthetic Golden-Set Generator

EXT-05

Source: DataDesigner — config-driven generation of diverse test inputs with LLM-as-judge validation

  • Upgrade TEST-12 (golden-set creation) from manual authoring to a script-driven approach. A scripts/gen-golden-set.mjs script reads a YAML config defining prompt templates, constraint fields, and expected response criteria — then generates 20–50 diverse test cases by sampling across template variables.
  • Each generated test case runs through a lightweight LLM judge pass (using callAI() via /api/ai) that scores the response against the expected criteria on a 0–100 scale. Cases scoring below 70 are flagged for human review before being committed to the golden set.
  • Commit the generated golden set to __tests__/golden/ as plain JSON. The existing eval:agent-runtime script reads from this directory. Re-generation is opt-in via npm run gen-golden-set and requires a human review step before committing updated cases.

11.6 LLM-as-Judge Eval Scorer

EXT-06

Source: DataDesigner — built-in LLM-as-judge scoring, multi-axis quality assessment

  • Add a judge eval category to the runtime eval harness. For each agent response in the eval set, a second LLM call evaluates the response on four axes: accuracy, relevance, grounding (no hallucination), and safe behavior. Each axis scores 0–25 for a 0–100 total.
  • The judge prompt is intentionally adversarial — it looks for overconfident claims, unsupported assertions, and policy violations. Judge scores feed the existing AgentEvalResult type as a new judgeScore field alongside the existing category scores.
  • Surface the judge score as its own category bar in the Settings eval trend panel and in the HQ Telemetry HUD eval chip. CI gate threshold: --min-category judge=75.

11.7 Dry-Run / Preview Mode for Missions

EXT-07

Source: DataDesigner — preview mode shows what tools would fire before committing

  • Add a "Preview Run" button to the HQ scheduler UI alongside the existing "Run Now / Force" controls. A preview run executes the agent loop with all write tools shimmed — they log what they would do but make no actual changes. Read tools execute normally so context is real.
  • The preview result renders in the HQ chat panel as a structured "Mission Preview" card: list of tools that would have been called, estimated token cost, projected output artifacts, and any detected precedent conflicts. The operator can then choose to execute the real run or cancel.
  • Preview runs are always free of cooldown restrictions. Real runs are still cooldown-governed. The distinction is shown clearly in the HUD so operators know they can preview freely without burning the cooldown window.

11.8 Dependency-Aware Memory Recall

EXT-08

Source: DataDesigner — dependency-aware column generation carries related facts together

  • Extend the planned recall_by_query tool (AI-03) to also return "correlated entries" — memory entries that share a tag, entity name, or were recorded within 5 minutes of the matched entry. Return correlated entries in a separate related array in the tool response.
  • The agent prompt template for recall_by_query instructs the model to use both the primary match and the related array before answering, reducing the chance of a correct-but-incomplete response that ignores a directly relevant connected fact.

11.9 Validator Pipeline for Agent Writes

EXT-09

Source: DataDesigner — validator chain (Python, SQL, custom remote) runs after every generated field

  • Extend the existing /api/verify adapter chain to run automatically after any write_file or patch_project_file tool call resolves. Chain: (1) TypeScript type-check on the touched file, (2) ESLint on the touched file, (3) route smoke against /api/health. All three must pass for the write to be marked verified.
  • If any validator fails, the agent run status is immediately downgraded to degraded and the write artifact is quarantined — stored in AgentRunArtifact.pendingEdits with a verificationFailed flag. The operator HUD shows the failure reason and the raw diff so the operator can decide whether to revert.
  • Add a "Revert write" action to the operator HUD for quarantined artifacts. The revert calls the existing write_file tool with the pre-write snapshot stored at write time. No git operations needed — snapshot is held in memory for the session duration.

11.10 n8n Workflow Templates Integration

EXT-10

Source: n8n template search — four high-signal templates aligned to Nexus capabilities

  • Open Deep Research (template 2883, 21k views): Iterative multi-query research with SerpAPI + Jina AI. Port the query-expansion logic into the NOVA agent prompt — NOVA already does web search, but adding explicit multi-query generation (3–5 sub-queries per research task) and a source-evaluation step significantly improves output fidelity.
  • Crypto Alpha Scanner (template 5632): Whale tracking + DEX monitoring pattern. Map this into the FLUX agent's data-gathering pass. FLUX already reads live prices — extending to on-chain whale wallet alerts via a free public endpoint (e.g., Whale Alert free tier) gives FLUX a signal it currently lacks.
  • Startup Intelligence Monitoring (template 4792): Crunchbase + AI summaries + email alerts pattern. Map to a new scheduled NOVA mission: weekly funding-round sweep using Crunchbase's public search (no key required for basic results) → NOVA summary → Telegram alert. Follows the existing Auto Ops cooldown pattern.
